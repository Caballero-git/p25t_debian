* What this is
  Mainline Linux (7.3-rc) and Debian 13 "trixie" (arm64) running on the
  Teclast P25T (board P9A6, Rockchip RK3566, RK817 PMIC, 4 GB LPDDR4X),
  booted entirely from a microSD card. The internal eMMC (Android 12) is
  never written: remove the card and the tablet is stock again.

  The bootloader is locked. We do not need to unlock it: the stock SPL
  tries the SD card first and loads our U-Boot from a GPT partition named
  ~uboot~ (see [[file:docs/boot.org][docs/boot.org]]).

* Quick start (outline)
  Details in the docs; each step has its own script.
  1. Build U-Boot (~u-boot/p25t-u-boot.config~) and the kernel
     (~kernel/patches~, ~kernel/p25t-kernel.config~).
  2. ~u-boot/build_sd_image.sh~ → an SD image with U-Boot, kernel, DT, initramfs.
  3. ~tools/write_sdcard.sh~ → write it to the card (checks the device, verifies).
  4. ~debian/build_debian.sh~ then ~debian/install_debian.sh~ → Debian on the card.
  5. ~install/pc_install_stage5.sh~ → Wi-Fi driver and network (from the PC).
  6. ~install/bt_install.sh~ → Bluetooth (on the tablet).
  7. Insert the card, power on. Debian logs in on the screen and over SSH.

* Safety rules followed throughout
  - Never write to the eMMC. Every script checks that its target is a
    removable/USB disk.
  - Writes to the RK817 power chip only after an explicit, reviewed proposal.
    The DT describes only the rails Linux must control - RK817 BOOST,
    OTG_SWITCH, DCDC_REG2 (vdd_gpu), LDO4 (vccio_acodec) and the SYR837
    (vdd_cpu) - each with values copied from the stock DT. Every other rail
    stays as the bootloader left it.
  - Recovery path for the eMMC is the official firmware image (RKDevTool),
    not our backup (see the backup caveat in [[file:docs/findings.org][findings]]).

* Working pipeline
  The standing order of operations for any change (a patch, a DT tweak, a
  script, a config fix) — in order, not skipped or reordered:
  1. *Make* the change (patch, script, config).
  2. *Test* it on the real hardware.
  3. *If it works*, in this order:
     a. update the relevant doc(s) (~docs/hardware.org~,
        ~docs/kernel.org~, ~docs/debian.org~, ~docs/todo.org~ — whichever
        the change touches) — verified by read-back/checksum, as always;
     b. sync the changed files into this ~p25t-linux/~ tree (PC side);
     c. commit and push to GitHub (~push_to_github.sh~).
  4. *Only once 3 is fully done* (docs updated, synced, committed,
     pushed) — clean up the scratch/one-off files the change used along
     the way: install tarballs and their extracted folders, one-shot
     stage scripts and their logs, loose DTB/Image copies left in a home
     directory, anything that isn't ~tests/test_NN.sh~/~result_NN.txt~
     (those stay, see "Test scripts" in [[file:docs/debian.org][debian]])
     or the eMMC/Android recovery kit (never touched by this rule).
  NEVER DELETE THE LINUX KERNEL CHECKOUT (~linux/~, the ~git clone~ from
  "Get the source and apply" in [[file:docs/kernel.org][kernel]]) OR ANY
  OTHER PERSISTENT BUILD TREE AS PART OF STEP 4. Unlike the one-shot
  items step 4 targets, it is not scratch left over from a single
  change — it is reused, patch after patch, for every future one, and
  every patch already applied to it lives there only as uncommitted
  git history until the next ~format-patch~. Lost 2026-09-28 in a
  general cleanup pass that didn't carve out this exception; recovered
  only because every patch was also saved separately under
  ~kernel/patches/~, letting the tree be rebuilt from a fresh clone
  plus ~git am kernel/patches/*.patch~ - do not rely on that safety net
  a second time.
  If a change *doesn't* work, none of step 4 applies - keep everything
  around until it's diagnosed, exactly as this project has done so far.
  The point of step 4 coming *last*: nothing gets deleted before it's
  both working and safely saved in at least two places (docs + git
  history), so a cleanup can never be the reason something is lost.
