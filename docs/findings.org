#+TITLE: P25T — findings, lessons and dead ends
#+DATE: 2026-09-25
#+STARTUP: overview

* Booting without unlocking
  - ~fastboot flashing unlock~ was not needed. The stock SPL on the eMMC
    scans the microSD first for a GPT partition named ~uboot~ and loads a
    Rockchip-style FIT from it (copies at +0 and +4096 sectors). Putting
    mainline U-Boot + BL31 there gives full control while the eMMC stays
    untouched.
  - The FIT must be built with external data, 512-byte alignment and a
    4 KiB header area: ~mkimage -E -B 0x200 -p 0x1000~, with BL31 split into
    its ELF load segments (~u-boot/split_bl31.py~).
  - With no serial console, U-Boot writes an ~env export~ status note to a
    raw sector (1331200) at each step. Reading it on the PC told us how far
    each failed boot got. Keep that sector outside every partition.

* Display: HS commands, not LPM (the key fix)
  Symptom: backlight on, panel black; first DCS read times out (-110),
  then "failed to write command FIFO".
  - The stock DT asks for ~MIPI_DSI_MODE_LPM~ (flags 0xa03): commands in
    low-power escape mode. On mainline ~dw-mipi-dsi~ the JD9365 never
    reacts to LP commands.
  - Sending the same 202 commands in high-speed mode
    (flags 0x603: VIDEO | BURST | NO_EOT | CLOCK_NON_CONTINUOUS) works
    at once: Tux, then the console.
  - DCS reads never get an answer on this board. A failed read leaves data
    lane 0 turned around (~PHY_STATUS 0x1FBB~) and the video stops.
    *Never read from the panel.*
  - The pixel clock was 24 MHz instead of 67 MHz until VPLL was preset to
    1608 MHz in ~&cru~: ~dclk_vop1~ cannot change its parent's rate, and the
    stock U-Boot that used to set VPLL is no longer in the path.

* Display dead ends (so nobody repeats them)
  - Power rails ("rails" experiment, the first approved RK817 writes):
    LDO9 2.8 V, LDO8 1.8 V, LDO4 3.3 V switched on one by one with colour
    tests in between. No effect on the panel. Nothing was ever switched off.
  - vccio4/vccio6 1.8 V modes, GPIO4_A7, BOOST: irrelevant to the panel.
  - "yyk enable_stbyb" in the stock kernel is an optional GPIO the P25T does
    not define.
  - Comparing D-PHY settings with the stock kernel: equal once the clock
    was right; the difference was only LP vs HS.

* Display: every line 3 px late (porch, not polarity or clock)
  Symptom (seen in landscape, 2026-10-02): the top of the first console
  row missing and shown at the bottom; first character column hard to
  read; in portrait the top rows of aptitude's blue background looked
  wrong. ~tests/test_18.sh~ (coloured bars at each panel edge) made it
  measurable: along the panel line (portrait x) the last 3 px of a line
  appeared at the start of the next; rows near the frame top flickered
  on colour (not on black).
  - The timing values were already the stock ones. Two other stock
    settings were tried first, each a kernel build:
    - continuous DSI clock lane (stock ~dsi,flags~ minus LPM, 0x203)
      plus negative sync: panel black, init "result 0", no errors;
    - negative hsync/vsync alone: picture up, flicker gone, but colour
      channels rotated by one byte (blue -> red, red -> green, green ->
      blue) and a ~20 px wrap. The sync polarity moves where the DSI
      host picks up the pixel data; positive is right on this board.
  - Fix: 3 px from the back porch to the front porch (hfp 21, hbp 15).
  - Method that ended the guessing: let the driver read the timing from
    a DT ~panel-timing~ node (patch 0024) and edit the DTB on the card
    (~tests/tune_panel.sh~, ~fdtput~) - one reboot per try instead of a
    kernel build. Right at the first try.
  - Mistake to avoid: an observation (emacs, whole row wrapped) was
    taken for the result of a build that had not been deployed yet.
    Always tie each observation to the kernel that was running
    (~uname -v~).

* USB gadget: DWC3 quirks and PHY tuning
  Symptom: "failed to enable ep0out" on the tablet, ~-71~ (EPROTO) on the PC,
  no enumeration.
  - Without ~snps,dis-u2-freeclk-exists-quirk~ the controller expects a
    free-running UTMI clock while the USB2 PHY is suspended (no cable).
    There is none, so enabling ep0 times out. The stock DT has this quirk
    plus ~dis_enblslpm~, ~dis-del-phy-power-chg~, ~dis-tx-ipgap-linecheck~.
  - The stock kernel also tunes the USB2 PHY (pre-emphasis, eye height,
    bvalid filter). Our initramfs applies the same values with ~devmem~.
  - Result: enumeration works, but not every boot. Plugging the cable in
    *before* power-on works best. Still open.

* Wi-Fi
  - The stock DT says ~rtl8723cs~; the chip is an *AIC8801*. The SDIO card
    ID and Android's loaded modules gave it away.
  - Needs: supply switch GPIO0_A0 (active low), WL_REG_ON GPIO0_C0,
    vccio4 in 1.8 V mode, and the RK817 32 kHz clock (already on at reset,
    register ~0xF2~ bit 7, so no PMIC write was needed).
  - The radxa-pkg driver builds up to 7.2 with its Debian patches; kernel
    7.3 changed four cfg80211 callbacks (see [[file:kernel.org][kernel]]).

* Bluetooth
  - Same AIC8801, plain H4 over UART1 at 1.5 Mbaud with RTS/CTS.
    BT_REG_ON (GPIO0_C1) held high by a GPIO hog; ~btattach~ from user space.
    No vendor driver needed.

* Backup caveat
  - The ~rkdeveloptool~ eMMC backup in loader mode only contains real data
    below sector 65536 (32 MiB): loader, security, uboot_a/b, trust_a/b,
    misc, dtbo_a. From dtbo_b onwards (vbmeta, boot_a/b, super, ...) it is
    ~0xCC~ filler. Loader-mode reads beyond 32 MiB are silently not real.
  - Recovery path for the eMMC is therefore the official ~Firmware.img~
    (flash with RKDevTool), not that backup. Check any backup with
    ~tools/verify_backup.py~.

* Android probing
  - Android refused to hand over the live DT (~/sys/firmware/fdt~); a
    bugreport gave the bound drivers and I2C devices instead
    (~tools/probe_android.sh~).
  - Found that way: vdd_cpu is a SYR837 at i2c0 0x40 (other candidates
    absent); touch GSL3673 at i2c1 0x40; both accelerometer drivers bound
    (SC7A20 0x19 and DA223 0x27), real chip unconfirmed.

* Touchscreen: four problems stacked on top of each other
  Symptom: "Registers clear error -6", no input device. Each fix revealed
  the next problem (2026-09-29/30, details in [[file:todo.org][todo]]):
  - *Reset NACK.* The GSL3673 NACKs the soft-reset byte because it resets
    before acknowledging. Found by replaying the driver's init writes one
    at a time with i2c-tools (~tests/test_06.sh~): exactly one write
    fails, and the chip answers straight after. Patch 0018 tolerates it.
  - *Wrong firmware.* A GSL3673 table taken from another product's GPL
    source uploads without a single error but never starts (status ~0xB0~
    stays 0) - even with the vendor's own start-up sequence replayed byte
    for byte. The right table was inside the tablet's own stock kernel;
    it worked first time. Same chip name and same I2C address are *not*
    enough to share firmware.
  - *Firmware not there at boot.* A built-in driver probes before the root
    filesystem exists, so ~/lib/firmware~ is empty for it:
    ~CONFIG_EXTRA_FIRMWARE~ builds the blob into the kernel.
  - *Coordinates.* The chip reports in its own rotated coordinate space;
    measured with a guided script (~tests/test_09.py~), not guessed.
  - Dead ends, so nobody repeats them: flipping ~power-gpios~ to
    active-low (made it worse: the chip then stays in reset); RK817 LDO9
    (not the touch supply); a longer wait after start-up (the firmware
    wasn't slow, it was wrong).

* Console: one getty on a dead tty (blinking cursor, dead VTs, hung reboot)
  Symptoms (for months): some boots showed only a blinking cursor on
  the panel; gettys started after boot (logind's tty4-6, the respawn
  after a logout) never gave a login; ~systemctl~ sometimes answered
  "Connection timed out"; a ~reboot~ could hang until power-off.
  Found 2026-09-30 with ~tests/test_10.sh~ (process stacks, not guesses):
  - ~p25t-gadget~ creates ~/dev/ttyGS0~ even when the gadget never
    binds (host mode) and nothing reads it without a USB host (no
    cable). Writes to it block.
  - systemd 257 resets a getty's terminal before starting agetty and
    holds a lock on ~/dev/console~ while doing it. The ~ttyGS0~ child
    blocked in that ~write()~ for ever, *holding the lock*
    (~result_10a~: pid 478 in ~n_tty_write~, fd 3 = ~/dev/console~).
  - Every getty whose child came later waited on the lock
    (~flock(3, LOCK_EX)~): ~ttyS2~ always, tty1-3 whenever ~ttyGS0~ won
    the start race by a few ms (the "blinking cursor" boots), and every
    getty started after boot (tty4 in ~result_10c~: empty screen).
  - On shutdown PID 1 resets the stopped gettys' terminals itself and
    got stuck the same way: last message "Stopped getty@tty1", then
    logind's D-Bus calls to PID 1 time out every 75 s
    (~result_10_shutdown~). Only a power-off recovered.
  - Fix: ~systemctl mask serial-getty@ttyGS0.service~ (done by
    ~p25t-setup.sh~). Verified: no stuck processes, tty1-3 prompts,
    on-demand tty4/tty6, fresh prompt after logout, clean reboot
    (~result_10e~-~10h~).
  - Lesson: never run a getty on a tty nobody reads. Also, a ~mask~
    only affects the next boot: if the unit is already stuck, the
    reboot that should apply the mask hangs on it - power-cycle.

* Speaker and torch: two pins the stock DT really meant (2026-10-01)
  - The stock DT is Rockchip's generic SDK file: it lists alternatives,
    and two nodes can name the same pin. GPIO3_A2 appears as the
    speaker-amp enable *and* as the accelerometer IRQ; the deciding
    detail was ~irq_enable = <0>~ on the sensor node. We took the wrong
    one in patch 0013: the speaker stayed off, and the IRQ fired 100000
    times at every boot until the kernel disabled it. Read *all*
    properties of a stock node, not only the pin.
  - A GPIO in an unpowered IO domain does nothing, without any error.
    The torch pin (GPIO4_A6) sits in vccio6, supplied by RK817 LDO8,
    which our boot left off. ~gpioset~ reported "output, high" and the
    LED stayed dark. Check the IO-domain supply before suspecting the
    pin.
  - Android is a cheap reference: booting it (card out) showed the
    torch, cameras, microphone and headphone detect all work, and adb
    (over Wi-Fi when USB isn't seen) gave the fitted sensors, their
    resolutions and the headphone IRQ pin without root.

* Boot time: a mail server and a gadget wait (2026-10-05)
  - ~systemd-analyze critical-chain~ shows what the boot really waited
    for; ~blame~ alone lists units that run in parallel and mislead.
  - A Recommends chain (emacs-nox → mailutils → a mail server) installed
    ~exim4~, which pulls in ~network-online.target~: every boot waited for
    Wi-Fi. Boot times of 17, 21 and 36 s were all the same cause, varying
    with the Wi-Fi. Check ~systemctl list-dependencies --reverse
    network-online.target~ after installing packages.
  - Our own ~p25t-gadget~ cost 20 s in host mode (waiting for a UDC that
    cannot appear). Scripts that wait for hardware must first check
    whether the hardware can exist in this configuration.
  - Capping the journal did not shorten its flush; measure before
    assuming size is the cost.

* Rear camera: the core supply, and a capture-block reset (2026-10-07)
  - Symptom (tests 22-37): the GC5035 probes, answers on I2C, the media
    graph works, STREAMON succeeds - but no MIPI high-speed clock, no
    frames. Ruled out one by one: supplies on, MCLK 24 MHz on the pad,
    PWDN polarity, D-PHY routing (full/split), Rockchip's own register
    sequence, the I2C read method.
  - test_36 found the switch: register ~0xfc~. With bit 0 set the
    sensor's logic runs from the raw 24 MHz input and its registers
    work; the table's final ~0xfc = 0x8e~ (bit 0 clear) moves it onto its
    PLL - and from then on every paged register write is lost. With
    ~0x8f~ (test_38/39) frames flowed but contained no image.
  - Logic that works slowly but dies when clocked fast = core supply too
    low. Stock DT: RK817 ~LDO_REG2~ is *named* "vdda_0v9" but *set* to
    1.2 V, always-on; our boot left it at 0.9 V (test_40). With LDO2 at
    1.2 V (test_42) the unchanged driver gives perfect colour bars.
    Fix: patch 0030. Lesson: compare the rails' *voltages* with stock,
    not only on/off - and don't trust a regulator's name.
  - Second trap, only visible once real frames flowed: the tablet froze
    hard (no kernel message) at the start of the *second* capture
    (test_41, test_43). Mainline ~rkcif~ resets the VICAP on runtime
    suspend, and that reset also hits its IOMMU; the next capture's DMA
    then goes wild. Keeping the VICAP runtime-active (~power/control =
    on~) fixes it (test_44: three captures, IOMMU paging on, no fault).
    Workaround: udev rule ~debian/99-p25t-vicap.rules~.
  - Small ones: frame 1 after stream-on is empty and the next ones are
    dark (keep the last frames of a longer capture); the real Bayer
    order is RGGB, not the GRBG the driver reports; a Python poke at
    receiver registers after the capture ended gives "Bus error"
    (block powered down) - harmless.
  - When a test may freeze the tablet: run it over ssh with ~| tee~ on
    the PC and ~sync~ after every step, or its output never reaches the
    disk (test_41 left an empty result file).

* Practical lessons
  - When the kernel log can't say *which* step failed, replay the
    driver's I2C sequence by hand with i2c-tools. Find the bus by its
    controller's address (~/sys/bus/i2c/devices/i2c-*~ → ~fe5a0000.i2c~),
    never by number, and check the DT node's ~compatible~ before
    writing: 0x40 is the touchscreen on i2c1 but the CPU regulator on i2c0.
  - Take vendor firmware from *this* device's own stock image
    (~tools/gsl_fw_from_stock_kernel.py~ for GSL tables), not from a
    similar product.
  - A script that switches configurations by copying fixed files
    (~set-usb-role.sh~) silently undoes every later change unless those
    copies are refreshed with each change. It also has to keep
    ~CARD-SHA256SUMS~ in step - it does now.
  - ~P25TBOOT~ can be changed from the tablet itself (mounted at
    ~/boot/firmware~ with ~flush~) - no card shuffling for kernel/DT
    deploys, as long as the new files boot.
  - 2026-09-29: writes to ~P25TBOOT~ through Claude's remote file bridge
    went wrong - one landed under a ~-1~ name, and the target ended up
    with other content (partly the role-switch problem above). Since then
    card files are written by Jose, locally, and checked with
    ~sha256sum -c CARD-SHA256SUMS~.
  - 2026-09-30: the ~-1~ names explained (most likely). The Claude
    desktop app copies files Claude saves in its session's /outputs/
    folder into the folders connected to the session, keeping their
    relative paths, and names a copy ~NAME-1.EXT~ when ~NAME.EXT~ already
    exists there. Seen in ~~/p25t-backup/p25t-linux/~: ~README-1.org~,
    ~docs/*-1.org~, ~tests/test_05-1.sh~ appeared before the sync
    tarball was unpacked, identical to the tarball's copies. ~P25TBOOT~
    was a connected folder on 2026-09-29 too. Rules since then: Claude
    keeps its working copy of this tree outside /outputs/ and hands over
    only tarballs with a checksum manifest; ~P25TBOOT~ stays out of the
    session's connected folders unless a card write is planned; after
    unpacking a sync, delete any ~*-1.*~ files once ~sha256sum -c~ passes.
  - Commands copied from the chat can lose a run of spaces: a pattern
    with the two spaces of a ~sha256sum~ line (~hash  name~) then
    silently matches nothing (2026-10-01, ~CARD-SHA256SUMS~). Commands
    for Jose avoid depending on repeated spaces; e.g. replace the bare
    64-character hash instead.
    The same can happen to ~$~: ~H=$(...)~ arrived as ~H=(...)~ (a bash
    syntax error, nothing ran). For critical files give the literal
    values, no shell variables.
    Again 2026-10-04: a ~for d in ...; do udevadm info "$d"~ loop arrived
    as ~"d"~. Anything with variables or loops goes into a script file
    in the repo, not into a command to paste.
  - Measure against a control. ~test_15~ recorded "talk now" clips
    without a silent reference and got noise; it looked like a dead
    mic, and a theory (no bias, LDO9) was built on it. ~test_16~
    recorded QUIET and TALK pairs and showed +37 dB: the mic had worked
    all along. Recording tests now always record a quiet/talk pair.
  - Everything that writes to a disk checks first that the target is a
    removable/USB disk, and verifies by checksum afterwards
    (~CARD-SHA256SUMS~ on ~P25TBOOT~).
  - Keep the previous kernel/DT on the card (~*.stageN~): rollback is a
    file copy on the PC.
  - A boot-log on the card (initramfs snapshots and the Debian
    ~p25t-bootlog~ timer) replaces the missing serial console.
  - Two machines, two prompts: ~jose@hp240~ is the PC, ~jose@p25t~ the
    tablet. Paths like ~~/p25t-backup~ exist only on the PC.
