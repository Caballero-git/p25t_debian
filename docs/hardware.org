#+TITLE: Teclast P25T (P9A6) — hardware
#+DATE: 2026-09-25
#+STARTUP: overview

* Sources
  - Stock firmware ~P25T(P9A6)_Android 12.0_ROW_V1.01_20230207~ → ~boot.img~
    → device tree blob (unpacked with ~tools/rkunpack.py~, searched with
    ~tools/dtbscan.py~ and ~tools/fdtgrep.py~).
  - Stock DT: ~model = "Rockchip RK3566 RK817 TABLET LP4X Board"~,
    ~compatible = "rockchip,rk3566-rk817-tablet", "rockchip,rk3566"~.
    It is Rockchip's generic SDK tablet DT and lists alternative parts
    (four vdd_cpu regulators, two accelerometers, twelve cameras, Wi-Fi
    type "rtl8723cs"). Only the ones present probe.
  - Runtime checks on Android (~tools/probe_android.sh~, a bugreport) and
    read-only register dumps from our own initramfs.
  - The Android ~dtbo.img~ overlay (559 bytes) only sets boot devices and
    reboot-mode magic numbers.

* GPIO naming
  - Controllers: gpio0 ~fdd60000~, gpio1 ~fe740000~, gpio2 ~fe750000~,
    gpio3 ~fe760000~, gpio4 ~fe770000~.
  - Pin n of a bank → port letter ⌊n/8⌋ (A, B, C, D) and index n mod 8.
    Example: gpio0 pin 18 → GPIO0_C2.
  - Pad level register ~EXT_PORT~ at controller + ~0x70~. A pad whose IO
    domain is unpowered reads 0 even if its output register says 1.

* Power (RK817 and SYR837)
  - RK817 enable registers have per-bit write-enable masks (high nibble =
    mask, low nibble = enable). Example: writing ~0x88~ to ~0xB3~ changes
    only LDO8.
  - 32 kHz clock output for Wi-Fi is already on at boot (RK817 register
    ~0xF2~ bit 7). No write needed.
  - Rails that Android keeps always-on but our boot leaves at reset default:
    | RK817 rail | stock name   | stock V     | stock user       | state in our boot            |
    |------------+--------------+-------------+------------------+-------------------------------|
    | LDO9       | vcc2v8_dvp   | 2.8 V       | none listed      | off                           |
    | LDO8       | vcc1v8_dvp   | 1.8 V       | IO domain vccio6 | on since patch 0022 (always-on, as stock) |
    | LDO4       | vccio_acodec | 3.3 V       | IO domain vccio1 | on since patch 0015           |
    | BOOST      | boost        | 4.9–5.4 V   | feeds OTG_SWITCH | host-mode DTB only (patch 0010) |
    | OTG_SWITCH | otg_switch   | (switch)    | USB-C VBUS gate  | on, host-mode DTB only       |
    Turning LDO4/8/9 on was tested ("rails" experiment): irrelevant to the
    panel. They matter for audio (LDO4, patch 0015) and the camera side:
    LDO8 feeds IO domain vccio6, and without it no GPIO4 pin can drive
    anything (torch, vcc_camera, camera reset/pwdn) - patch 0022. LDO9 is not the
    touchscreen's supply either (switched on 2026-09-29, ~tests/test_08.sh~:
    no change; touch works with it off).
  - Our DT uses dummy fixed regulators (~vcc_sys_dummy~, ~vcc_3v3_dummy~,
    ~vcc_1v8_dummy~) so Linux never switches a real rail — *except* BOOST
    and OTG_SWITCH (patch 0008, 2026-09-26): a minimal ~pmic@20~ node under
    ~&i2c0~ with only these two regulators, values copied verbatim from the
    stock DT (~Firmware/dt/boot-0-0x6c0fe00.dts~). ~OTG_SWITCH~ is the actual gate onto the
    USB-C VBUS pin; it is only ever requested via ~usb2phy0_otg~'s
    ~phy-supply~ in the *host-mode* DTB (~rk3566-teclast-p25t-usbhost.dts~)
    — the normal/peripheral DTB never references it, so it stays off there,
    same as before this patch. This was needed because without it, the USB
    host port had no VBUS at all: xHCI came up fine (once
    ~CONFIG_USB_XHCI_HCD~ was also enabled, see [[file:kernel.org][kernel]])
    but no bus-powered device — receiver or wired keyboard — could signal
    its presence with no 5 V on the line. Confirmed fixed 2026-09-26.
  - Patch 0009 (2026-09-26) adds the ~charger {}~/~battery {}~ pair inside
    the same ~pmic@20~ node, in the *shared* base DT (applies to both the
    normal and host-mode DTBs, unlike BOOST/OTG_SWITCH which are
    host-mode-only in effect). Values (design capacity, OCV table,
    charge-termination/max-current/max-voltage) copied from the stock DT's
    ~rk817,charger~/~rk817,battery~ properties and converted to the generic
    ~simple-battery~/~monitored-battery~ shape the mainline
    ~rk817_charger~ driver expects — a different binding, not a verbatim
    copy. Confirmed 2026-09-26: ~rk817-battery~/~rk817-charger~ both probe,
    reporting ~Charging~, ~Standard~ charge type, ≈1.10 A, USB type
    correctly detected as ~DCP~ (a dedicated charging port). See
    [[file:kernel.org][kernel]] for the full writeup, including two driver
    quirks worth knowing (charge-enable is left at hardware default; the
    USB input-current limit is hardcoded to 1.5 A rather than read from
    the DT, versus the stock 2 A).
  - Patch 0010 (2026-09-26, from a battery-consumption review): ~BOOST~
    had been ~regulator-always-on~/~regulator-boot-on~ in the *shared*
    base file since patch 0008 — unlike the stock DT, which has no
    always-on flag on it at all. Moved those two lines out of the base
    file and into an override in the host-mode DTB only (nothing else
    references ~BOOST~/~OTG_SWITCH~, checked before building), so the 5V
    boost converter is now live only while host mode is actually in use,
    not 24/7. The host-mode DTB's override reconstructs the identical
    property set, so it compiled *byte-for-byte identical* to before —
    zero regression risk there. Confirmed 2026-09-26: ~boost~ shows
    ~disabled~ in normal mode; charger/battery unaffected.
  - Patch 0011 (2026-09-26): real ~vdd_cpu~ (SYR837, ~silergy,syr827~ @
    i2c0 0x40) wired as ~cpu-supply~ on ~&cpu0~-~&cpu3~, for full DVFS.
    ~cpufreq-dt~ had been silently frequency-scaling already (config was
    already enabled, ~rk3566.dtsi~'s OPP table came in for free via
    ~#include~) but never touched voltage with no regulator attached.
    Values copied verbatim from the stock DT's ~syr837@40~ node (min/max
    712.5 mV–1.5 V, ramp-delay, ~fcs,suspend-voltage-selector~,
    always-on); stock's own ~regulator-init-microvolt~/
    ~regulator-initial-state~ have no mainline binding (checked) and were
    dropped, so probing only reports the chip's existing state, never
    forces a voltage. Confirmed 2026-09-26: ~dmesg~ shows a clean detect
    (~FAN53555 Option[8] Rev[1] Detected!~, no errors); voltage tracks
    frequency exactly against ~rk3566.dtsi~'s OPP table — 1.025 V at
    1416 MHz idle, 1.15 V at 1800 MHz under load, both exact OPP targets.
    See [[file:kernel.org][kernel]] for the full writeup.

* IO domains
  - Boot state: all domains in 3.3 V mode (PMU_GRF ~IO_VSEL0 = 0x00~,
    ~IO_VSEL1 = 0xFF~).
  - vccio4 (sdmmc1 / Wi-Fi + UART1) must be in 1.8 V mode: our DT sets
    ~&pmu_io_domains { vccio4-supply = <&vcc_1v8_dummy>; }~.

* Battery reading without a driver
  Read-only. Battery voltage is in RK817 registers ~0x78~ (high byte) and
  ~0x79~ (low byte), on i2c bus 0, chip address 0x20:
  #+begin_src sh
  sudo i2cget -y -f 0 0x20 0x78 b
  sudo i2cget -y -f 0 0x20 0x79 b
  #+end_src
  ~<RAW>~ = high × 256 + low. The chip's own calibration pair (registers
  ~0x93~–~0x96~) gives k = 70 and b = 14, the same formula the mainline
  ~rk817_charger~ driver uses:

  V (µV) = 70 × <RAW> + 14 × 1000

  Worked example (2026-09-25, full battery): high ~0xee~, low ~0x16~,
  <RAW> = 0xee16 = 60950 → V = 4 280 500 µV ≈ 4.28 V.

* Panel
  - Timings: pixel clock 67 MHz; horizontal 800 active, *21/18/15*
    (front/sync/back; stock 18/18/18 shows every line 3 px late, see
    findings); vertical 1280 active, 12/4/8. Positive sync (the stock
    negative polarity rotates the colour channels). In the DT as a
    ~panel-timing~ node (patches 0024, 0025).
  - Stock ~dsi,flags = 0xa03~ (VIDEO | BURST | NO_EOT | LPM). *On mainline
    use 0x603* (VIDEO | BURST | NO_EOT | CLOCK_NON_CONTINUOUS, no LPM),
    see [[file:findings.org][findings]]. A continuous clock (0x203)
    leaves the panel black (2026-10-02).
  - Init sequence: 202 two-byte DCS writes. Page select ~E0 xx~, unlock
    ~E1 93 / E2 65 / E3 F8~ (the JD9365 signature), then Sleep Out ~11~
    (+120 ms) and Display On ~29~ (+100 ms). Exit: ~28~ (+1 ms), ~10~ (+3 ms).
    Converted to driver syntax in ~kernel/p25t-panel-init.c.inc~.
  - Delays: prepare/reset/init 20 ms, enable 120 ms, disable/unprepare 20 ms.
  - Pixel clock source: VPLL preset to 1608 MHz in ~&cru~ (1608 / 24 = 67 MHz).

* Touchscreen (Silead GSL3673)
  - Stock DT: ~ts@40~ on i2c1, ~compatible = "GSL,GSL3673_800X1280"~,
    ~irq_gpio_number~ GPIO0_B0, ~rst_gpio_number~ GPIO0_C2; no supply
    listed. Mainline: ~silead,gsl3673~ with ~silead,gsl3670~ as fallback.
  - GPIO0_C2 is active-high: low holds the chip in reset (then even the
    ID read fails). IRQ is level-low. Needs no rail beyond what is on at
    boot (not LDO9).
  - Chip ID register ~0xFC~ reads ~0x50910000~.
  - Quirk: the chip NACKs the soft-reset write ~0xE0 <- 0x88~ - it resets
    before acknowledging, and answers normally right after. Mainline
    treated that as fatal; patch 0018 tolerates it.
  - Firmware: the vendor driver is built into the stock kernel with its
    firmware table as C data; the stock kernel holds three GSL tables
    (for ~GSL,GSL3673~, ~GSL,GSL3673_800X1280~, ~GSL,GSL_THZY~). Only the
    ~GSL,GSL3673_800X1280~ one works on this tablet (141 pages, sha256
    ~163a2a83...~); a GSL3673 table from another product uploads but
    never starts (status ~0xB0~ stays 0 instead of ~0x5A5A5A5A~).
    ~tools/gsl_fw_from_stock_kernel.py~ extracts it.
  - Upload takes ~3 s at i2c1's default 100 kHz (the vendor driver
    defines 350 kHz for writes).
  - Coordinates (raw, from the chip): ~0..1660 along the long axis
    (raw x, runs bottom to top in portrait) and ~0..880 along the short
    one (raw y, runs right to left). The DT inverts both and swaps
    (patch 0019). Multi-touch: 3 fingers tested, 10 slots.

* Wi-Fi and Bluetooth (AIC8801)
  - MAC addresses on this unit: Wi-Fi ~8c:35:92:f2:b5:45~,
    Bluetooth ~8C:35:92:F2:B5:46~.
  - Power sequence: vcc_wl (GPIO0_A0 low) with 100 ms start-up, then
    WL_REG_ON (GPIO0_C0) released 50 ms later (mmc-pwrseq-simple).
  - Firmware: ~/lib/firmware/aic8800_fw/SDIO/aic8800/~ (from the radxa package).
  - Bluetooth is a plain H4 UART device: no kernel driver needed beyond
    ~hci_uart~; ~btattach -B /dev/ttyS1 -P h4 -S 1500000~.

* USB-C (DWC3 + USB2 PHY0)
  - Stock DWC3 quirks: ~snps,dis_enblslpm_quirk~,
    ~snps,dis-u2-freeclk-exists-quirk~, ~snps,dis-del-phy-power-chg-quirk~,
    ~snps,dis-tx-ipgap-linecheck-quirk~.
  - Stock PHY tuning (~rk3568_usb2phy_tuning~ in the vendor kernel), applied
    by our initramfs with ~devmem~:
    | Address          | Change                     | Meaning                    |
    |------------------+----------------------------+----------------------------|
    | ~0xfe8a0030~     | bit 2 off, bits 6:4 = 6    | HS eye height 437.5 mV     |
    | ~0xfe8a0000~     | bits 2:0 = 4               | pre-emphasis on            |
    | ~0xfdca0048/4c~  | ~0x000f4240~               | 10 ms bvalid filter        |

* eMMC partitions (Android A/B, read-only for us)
  In order: loader, security, uboot_a, uboot_b, trust_a, trust_b, misc,
  dtbo_a, dtbo_b, vbmeta_a, vbmeta_b, boot_a, boot_b, backup, cache,
  metadata, frp, baseparameter, super (userdata follows).
  Bootloader state: locked. The loader-mode (~rkdeveloptool~) read only
  returned real data below sector 65536, see [[file:findings.org][findings]].
