  #+begin_src sh
  git clone https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

  git checkout -b p25t-bringup f2c53ea94

* Build
  ~LOCALVERSION=~ (empty) on the command line keeps the release name exactly
  ~7.3.0-rc4-p25t~ (the ~-p25t~ comes from ~CONFIG_LOCALVERSION~; the
  ~+~ git suffix is suppressed). Module paths depend on it.
  #+begin_src sh
  make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- LOCALVERSION= -j$(nproc) Image dtbs modules
  #+end_src
  A full build takes longer than 10 minutes on a small machine; run it with
  ~nohup~ if the session may time out.

  Results:
  | File                                                 | Goes to                          |
  |------------------------------------------------------+----------------------------------|
  | ~arch/arm64/boot/Image~                              | ~P25TBOOT/Image~                 |
  | ~arch/arm64/boot/dts/rockchip/rk3566-teclast-p25t.dtb~ | ~P25TBOOT/rk3566-teclast-p25t.dtb~ |
  | modules (~make modules_install INSTALL_MOD_PATH=<STAGING-DIR>~) | ~/usr/lib/modules/7.3.0-rc4-p25t/~ on ~p25troot~ |

  Debian trixie has ~/lib~ → ~/usr/lib~, so package everything under ~usr/~.

* Device tree notes
  - Real rails are *not* described: dummy fixed regulators stand in, so
    Linux never switches the RK817 or the SYR837 (see the safety rules).
  - ~&cru~ presets VPLL to 1608 MHz for the 67 MHz pixel clock;
    ~DCLK_VOP1~ is parented to VPLL.
  - DSI panel node: ~compatible = "teclast,p25t-panel"~, reset GPIO3_C3,
    ~vdd-supply = <&vcc_lcd>~ (fixed regulator on GPIO3_B1).
  - ~&usb_host0_xhci~: ~dr_mode = "peripheral"~, ~maximum-speed = "high-speed"~,
    PHY ~usb2phy0_otg~, plus the four stock quirks.
  - ~&cru~ also presets RTC 32k, GPLL 1200 MHz and PPLL 200 MHz (stock values).
  - Wi-Fi: ~vcc_wl~ (GPIO0_A0, active low, 100 ms start-up),
    ~sdio_pwrseq~ (reset GPIO0_C0 active low, 50 ms post-power-on),
    ~&sdmmc1~ 4-bit 50 MHz non-removable, ~&pmu_io_domains~ vccio4 = 1.8 V,
    alias ~mmc2 = &sdmmc1~.
  - Bluetooth: ~&uart1~ with ~uart1m0~ xfer/ctsn/rtsn and ~uart-has-rtscts~;
    GPIO hog ~bt-reg-on-hog~ on GPIO0_C1 output-high.

* Panel driver (~panel-jadard-jd9365da-h3.c~)
  - New ~teclast_p25t_desc~: 800×1280, 67 MHz, 4 lanes, RGB888.
  - ~mode_flags = MIPI_DSI_MODE_VIDEO | MIPI_DSI_MODE_VIDEO_BURST |
    MIPI_DSI_MODE_NO_EOT_PACKET | MIPI_DSI_CLOCK_NON_CONTINUOUS~ (0x603).
    *Do not add ~MIPI_DSI_MODE_LPM~* and never issue DCS reads
    (see [[file:findings.org][findings]]).
  - After the init table the driver only logs
    ~p25t: init sequence sent...~.

* USB-C host-mode test variant (patches 0007, 0008) — working
  - Adds a *second* board file, ~kernel/rk3566-teclast-p25t-usbhost.dts~,
    which ~#include~s the normal one and overrides
    ~&usb_host0_xhci { dr_mode = "host"; };~ plus ~&usb2phy0_otg { phy-supply
    = <&rk817_otg_switch>; };~ (patch 0008, see below). Built as an extra
    Makefile target, ~rk3566-teclast-p25t-usbhost.dtb~ — the normal DTB is
    untouched, both are just files.
  - Purpose: try a USB wireless keyboard/mouse receiver on the tablet's
    single USB-C port. The port is one physical DWC3 controller, so it is
    either the gadget console + ~usb0~ network (normal DTB) or a USB host
    for a receiver (this DTB) — never both at once with our current DT.
  - Swap it in and out on ~P25TBOOT~ with
    ~usbhost_toggle.sh~ (see [[file:debian.org][debian]], "USB host-mode test");
    it keeps a backup of the normal DTB so switching back is a plain
    file copy, no rebuild needed.
  - Confirmed working 2026-09-26: a wired USB keyboard and a Logitech
    USB receiver (keyboard + mouse) both enumerate and register
    ~input:~ devices; typing works on the console. Getting here needed
    two separate fixes on top of the plain ~dr_mode = "host"~ change:
    1. *Kernel config*: ~CONFIG_USB_XHCI_HCD~/~CONFIG_USB_XHCI_PLATFORM~
       were off (this kernel was built for gadget-only use). ~dwc3~ still
       bound and created its ~xhci-hcd~ child device, but nothing in the
       kernel could drive it — no root hub, no ~lsusb~ output, no
       ~xhci_hcd~ lines in ~dmesg~ at all. Both are now ~y~ in
       ~p25t-kernel.config~.
    2. *VBUS power* (patch 0008): with xHCI working, the root hub showed
       up but nothing plugged in was ever detected — no bus-powered
       device can signal its presence with no 5 V on the line. The stock
       Android DT (~Firmware/dt/boot-0-0x6c0fe00.dts~) showed why: RK817's
       ~BOOST~ rail (5 V, always-on there) and ~OTG_SWITCH~ (the actual
       gate onto VBUS, switched by Android's own USB HAL) were both
       absent from our tree - we had no RK817 node at all. Patch 0008
       adds a minimal one (just these two regulators, values copied from
       stock) and links ~OTG_SWITCH~ to ~usb2phy0_otg~ via ~phy-supply~,
       only in this host-mode DTB - see [[file:hardware.org][hardware]]
       and [[file:todo.org][todo]] for the full writeup.
  - This is still a stand-in for real OTG dual-role support (auto-switching
    by cable/ID pin), which the stock DT has the hardware for (Type-C PD
    chips, ~extcon~, ~usb-role-switch~) but we never wired up — see
    [[file:todo.org][todo]].

* RK817 charger + battery (patch 0009) — working
  - Adds a ~charger {}~ subnode inside ~pmic@20~ (~monitored-battery~,
    sense resistor, sleep-current thresholds) and a top-level
    ~battery: battery {}~ node (~simple-battery~), both in the shared base
    DT — applies to the normal and host-mode DTBs alike, unlike patch 0008.
  - Binding is the *generic* Linux ~power_supply_battery_info~ scheme
    (~monitored-battery~ phandle + a ~simple-battery~ node), not the stock
    vendor ~rk817,charger~/~rk817,battery~ properties — different shape,
    values copied from the stock DT and converted (design capacity, OCV
    table, charge-termination/max-current/max-voltage), cross-checked
    against ~rk3566-pinetab2.dtsi~ (a real mainline board using the same
    driver).
  - Confirmed working 2026-09-26, on cable power:
    #+begin_src sh
    ls /sys/class/power_supply/
    cat /sys/class/power_supply/*/uevent
    #+end_src
    ~rk817-battery~ and ~rk817-charger~ both probed.
    ~POWER_SUPPLY_STATUS=Charging~, ~CHARGE_TYPE=Standard~,
    ~CURRENT_AVG~ ≈ 1.10 A, ~USB_TYPE=Unknown [DCP]~ (port correctly
    recognised as a dedicated charging port, not a data host).
  - The mainline ~rk817_charger.c~ driver never touches the chip's own
    charge-enable bit (~RK817_CHRG_EN~, ~CHRG_TERM~ register bit 6) — it
    only programs voltage/current *limits* and reads back status; charging
    enable is left at the chip's power-on-reset default. It also hardcodes
    the USB input-current limit to 1.5 A (not read from any DT property),
    versus the stock DT's ~max_input_current = 2000mA~ — a real but modest
    cut to charge rate, not something this patch introduced a way to fix
    without patching the driver itself.
  - ~dmesg | grep -iE "rk817.charg|rk817.batt|power_supply"~ comes back
    *empty* even on a working probe — checked the source, not a red flag.
    ~rk817_charger_probe()~ only calls ~dev_info~ when it has to correct an
    out-of-range DT value (max voltage/current outside sane limits); ours
    are in range, so those never fire. Everything else in the probe path
    is ~dev_dbg~ (silent unless dynamic debug is on) — there is no
    "probed OK" line in this driver at all. Use the
    ~/sys/class/power_supply/~ check above instead.

* Scope RK817 BOOST always-on to host-mode only (patch 0010) — working
  - Follow-up from a battery-consumption review (2026-09-26): patch 0008
    made ~BOOST~ ~regulator-always-on~/~regulator-boot-on~ in the *shared*
    base DT, so it ran 24/7 even in normal/peripheral mode, where nothing
    consumes it. Needed at the time so ~OTG_SWITCH~'s ~phy-supply~ link
    would have real 5V behind it once host mode was requested — but the
    stock DT itself has no always-on flag on ~BOOST~ at all.
  - Fix: removed the always-on/boot-on lines from ~&rk817_boost~ in the
    base file (~rk3566-teclast-p25t.dts~), added them back as an override
    only in the host-mode file (~rk3566-teclast-p25t-usbhost.dts~), same
    pattern as the existing ~&usb2phy0_otg { phy-supply = ...; };~
    override. Checked before building: nothing else in either DTB
    references ~rk817_boost~/~rk817_otg_switch~, so nothing else could be
    riding on this rail.
  - Because the override reconstructs the exact same property set, the
    *host-mode DTB compiled byte-for-byte identical* to before this patch
    (same sha256) — zero regression risk on the already-confirmed
    USB-receiver path. Only the base/normal DTB's binary changed.
  - Confirmed working 2026-09-26, cable power, normal mode:
    #+begin_src sh
    for d in /sys/class/regulator/regulator.*/; do
      echo "$d $(cat "$d"name 2>/dev/null) $(cat "$d"state 2>/dev/null)"
    done | grep -i boost
    #+end_src
    → ~boost ... disabled~ (previously ~enabled~). Charger/battery
    (patch 0009) unaffected: still ~Charging~, capacity rising normally.

* Real vdd_cpu / CPU DVFS (patch 0011) — working
  - Context: ~cpufreq-dt~ had been silently active with *frequency-only*
    scaling since before this patch — nobody had to add anything for that
    part. ~rk3566.dtsi~ already ships a standard ~cpu0_opp_table~ (408
    MHz–1.8 GHz, ~opp-shared~) wired to all four ~&cpuN~ nodes, and our
    ~.config~ already had ~CONFIG_CPU_FREQ~, ~CONFIG_CPUFREQ_DT~,
    ~CONFIG_CPUFREQ_DT_PLATDEV~ and the ~schedutil~ governor enabled.
    Confirmed active before this patch: ~scaling_available_frequencies~
    listed all 7 steps, ~scaling_governor~ was ~schedutil~. What was
    missing was voltage scaling - with no ~cpu-supply~, the CPU sat at
    whatever fixed voltage the bootloader set for its max frequency, even
    while idling at 408 MHz.
  - The real chip on this board: checked the stock DT, which lists *four*
    alternative vdd_cpu parts (generic Rockchip SDK board file - not all
    populated); only ~syr837@40~, ~compatible = "silergy,syr827"~, i2c0
    address 0x40, is actually on this tablet. Mainline already has a
    driver for this exact chip family: ~drivers/regulator/fan53555.c~
    (~CONFIG_REGULATOR_FAN53555=y~, already built).
  - Added a ~vdd_cpu: regulator@40~ node in ~&i2c0~ (shared base file,
    applies to both DTBs, like patch 0009), values copied verbatim from
    the stock DT's ~syr837@40~ node: min 712500 µV, max 1500000 µV,
    ramp-delay 1000, ~fcs,suspend-voltage-selector = 1~,
    ~regulator-always-on~ (stock has no ~regulator-boot-on~ on this node
    either - matched exactly). Stock's own ~regulator-init-microvolt~ and
    ~regulator-initial-state~ have *no mainline binding* - checked
    ~drivers/regulator/core.c~, ~of_regulator.c~, and the
    ~fcs,fan53555.yaml~ binding doc, none of them recognise either
    property - so both were dropped; probing this regulator only reports
    the chip's existing state, it never forces a voltage on boot.
    ~vin-supply~ mirrors stock's ~vcc3v8_sys~ via our existing
    ~vcc_sys_dummy~. The existing OPP table's voltage ceiling (1.15 V)
    sits well inside this chip's real range (712.5 mV–1.5 V), so the OPP
    table itself needed no changes.
  - Wired ~cpu-supply = <&vdd_cpu>;~ on ~&cpu0~ through ~&cpu3~, same
    pattern as ~rk3566-pinetab2.dtsi~ (a real mainline board using the
    same chip family, listed as a reference board - see the top of this
    file).
  - Confirmed working 2026-09-26, cable power: ~dmesg~ shows a clean,
    error-free detect -
    #+begin_src text
    fan53555-regulator 0-0040: FAN53555 Option[8] Rev[1] Detected!
    #+end_src
    and voltage tracks frequency exactly against ~cpu0_opp_table~'s
    targets - idle at 1416 MHz read back 1025000 µV (table target:
    1025000), under synthetic load at 1800 MHz (max) read back 1150000 µV
    (table target: 1150000). Both exact matches, not just "in range".
    Charger/battery sanity-checked unaffected in the same run.

* AIC8800 Wi-Fi/Bluetooth driver (out of tree)
  Source: [[https://github.com/radxa-pkg/aic8800][radxa-pkg/aic8800]], commit ~516e3b0~
  ("fix aic8800 sdio firmware load issue").
  #+begin_src sh
  git clone https://github.com/radxa-pkg/aic8800.git
  cd aic8800
  git checkout 516e3b0
  for p in $(cat debian/patches/series); do patch -p1 --forward -s < debian/patches/$p; done
  patch -p1 < ../p25t-linux/kernel/aic8800-fix-linux-7.3-build.patch
  cd src/SDIO/driver_fw/driver/aic8800
  make -C ../../../../../../linux M=$PWD ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- LOCALVERSION= modules
  #+end_src
  - Two USB-only Debian patches (~fix-usb-firmware-path~,
    ~fix-Lower-the-debugging-log-level~) fail to apply; they do not touch
    the SDIO driver and can be ignored.
  - The ~make -C~ path must point at the built kernel tree; adjust it to
    your layout (~<KERNEL-DIR>~).
  - Our 7.3 fix (only ~aic8800_fdrv/rwnx_main.c~):
    - ~cfg80211_probe_status()~ gained a ~link_id~ argument → pass ~-1~;
    - ~.probe_client~ became ~.probe_peer~, cookie passed by value;
    - ~remain_on_channel~ and ~mgmt_tx~ take the cookie by value; the
      wrappers use a local cookie.
  - Modules: ~aic8800_bsp.ko~, ~aic8800_fdrv.ko~ (and ~aic8800_btlpm.ko~,
    not needed for our UART Bluetooth) into
    ~/usr/lib/modules/7.3.0-rc4-p25t/extra/~, then ~depmod~.
  - Firmware: the package's ~aic8800_fw/SDIO/aic8800/~ folder into
    ~/usr/lib/firmware/aic8800_fw/SDIO/aic8800/~.
  - The install scripts (~install/wifi_install.sh~,
    ~install/pc_install_stage5.sh~) expect this in a tarball
    ~p25t-wifi.tar.gz~ with ~boot/~ (Image, DTB, ~SHA256SUMS~) and ~root/usr/~,
    ~root/etc/~.
