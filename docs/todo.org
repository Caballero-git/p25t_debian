* DONE Touchscreen (Silead GSL3673, i2c1 0x40, IRQ GPIO0_B0, reset GPIO0_C2)
  - *Working 2026-09-30*: touches, 3-finger multi-touch, correct
    orientation and range, from boot (no manual ~bind~). Patches
    0017-0020 plus ~CONFIG_EXTRA_FIRMWARE~, see [[file:kernel.org][kernel]].
    Verified with ~tests/test_05.sh~ (bound at boot, ~input: silead_ts~
    at 3.5 s) and ~tests/test_09.py~ (after the fix: nothing left to
    swap or invert, touches reach 14..884 x 22..1676 of 0..895 x 0..1679).
  - Four separate problems, found one at a time (2026-09-29/30):
    1. *Soft-reset NACK.* The chip NACKs the ~0xE0 <- 0x88~ reset write
       (it resets before acknowledging); mainline gave up with
       "Registers clear error -6". Pinned with ~tests/test_06.sh~, which
       replays the init writes one by one with i2c-tools: only that one
       fails, and the chip answers straight after. Patch 0018 tolerates
       exactly that NACK.
    2. *Wrong firmware.* The table from ~54shady/qop_kernel~ (source of
       patch 0017's firmware) uploads fine but never starts: status
       register ~0xB0~ stays 0, even with the vendor driver's exact
       start-up sequence replayed byte for byte (~tests/test_07.sh~). The
       stock kernel contains three GSL tables; the one belonging to
       ~GSL,GSL3673_800X1280~ (the stock DT's compatible) shares only 6
       of its 141 pages with the 54shady table. Extracted from
       ~Firmware/stock-kernel.bin~ with ~tools/gsl_fw_from_stock_kernel.py~,
       it worked first time.
    3. *Firmware not reachable at boot.* ~silead_ts~ is built in and
       probes at ~0.5 s, before the root filesystem is mounted: "Direct
       firmware load ... failed with error -2". Fixed by building the
       firmware into the kernel (patch 0020, ~CONFIG_EXTRA_FIRMWARE~).
    4. *Coordinates.* The chip reports ~0..1660 along the long axis and
       ~0..880 along the short one, rotated relative to the panel.
       Measured with ~tests/test_09.py~ (guided corners plus an edge
       sweep); patch 0019 sets the raw size with a margin (the input core
       inverts with unsigned ~max - x~, so out-of-range values would wrap,
       not clamp), both inversions and the swap.

    even the ID read fail); IRQ level-low is right; not a timing issue

  - History of the investigation (2026-09-28/29), kept for reference.
    Where it contradicts the outcome above, the outcome wins. The files
    it names under ~kernel/touchscreen/~ and ~tools/gsl3673_fw_convert.py~
    no longer exist (deleted 2026-09-30):
    - Mainline ~silead~ driver; the firmware blob must be extracted from the
      Android vendor partition and converted to the ~silead~ format.
    - Research pass (2026-09-28), no hardware touched, all from the kernel
      source tree and the web - what's actually needed before this can be
      built:
      - *Checked mainline's exact support*: ~drivers/input/touchscreen/silead.c~'s
        ~of_match_table~ lists exactly five compatibles - ~silead,gsl1680~,
        ~gsl1688~, ~gsl3670~, ~gsl3675~, ~gsl3692~. ~gsl3673~ is *not* one of
        them - a plain ~compatible = "silead,gsl3673"~ node would not bind at
        all.
      - *Good news, checked directly in the driver source*: the whole
        register map (~SILEAD_REG_RESET~/~DATA~/~POWER~/~CLOCK~/~STATUS~/~ID~,
        the 0x5A5A5A5A status-OK value, the I2C protocol) is identical across
        every compatible in that list - there is no per-chip branching
        anywhere in the driver. Silead kept one host protocol across the
        whole GSL family; the compatible list is a tested-devices allowlist,
        not a functional difference. So the standard two-string DT fallback -
        ~compatible = "silead,gsl3673", "silead,gsl3670";~ (informational
        real name first, a listed sibling second so the driver actually
        binds) - is low-risk here, the same technique already used
        elsewhere for an unlisted-but-compatible chip.
      - *Kernel config gap, same pattern as every previous one*:
        ~CONFIG_TOUCHSCREEN_SILEAD is not set~ in ~kernel/p25t-kernel.config~
        right now - would need enabling, same as ~CONFIG_SOUND~/~CONFIG_DRM_PANFROST~/
        ~CONFIG_IIO_ST_ACCEL_3AXIS~ before it.
      - *The actual hard part*: the firmware blob is a per-panel calibration
        table (offset/value pairs loaded into the chip's RAM at runtime, not
        baked into the silicon), so it cannot be borrowed from a different
        device's GSL3670/3673/etc firmware - it must be *this* P25T panel's
        own blob, extracted from Teclast's own Android driver.
      - *The tool for that already exists*:
        [[https://github.com/onitake/gsl-firmware][onitake/gsl-firmware]] -
        a community toolchain built for exactly this job. ~fw_extractor~
        pulls the firmware straight out of a vendor Android kernel module
        (a ~gslX680*.ko~-style file); ~untscfg~ does the same from a
        ~GSL_TS_CFG.h~-style vendor config header, if a ~.ko~ isn't found.
      - *Next concrete step, not yet done*: search the eMMC/Android recovery
        kit's ~Firmware.img~ (see [[file:hardware.org][hardware]] and
        [[file:findings.org][findings]]) for a Silead/~gslX680~ kernel module
        or config header - same read-only unpacking approach already used
        to identify the real Wi-Fi/BT chip earlier in this project. Needs
        the PC (large image, best with a real shell there) - couldn't be
        done from this research pass alone.
      - No web search turned up a published Teclast P25T (P9A6) GPL kernel
        source release specifically (other Teclast models do have one, e.g.
        the MT6753 TPad kernel on GitHub) - worth one more targeted look,
        but the ~Firmware.img~ module-extraction path doesn't depend on
        finding one.
      - *Firmware.img search (2026-09-28), confirms the chip and reveals the
        real complication*: ~strings~ on ~update/Image/boot.img~ (the actual
        Android kernel+ramdisk, not a mountable filesystem image) turned up
        over a dozen GSL3673-specific strings baked directly into the kernel
        binary itself - ~gsl3673~, ~GSL3673_FW~, ~GSL,GSL3673~,
        ~GSL,GSL3673_800X1280~, ~gsl3673_800x1280~, plus driver log strings
        (~"GSL3673 test_i2c error!"~, ~"gsl GSL3673 init failed"~,
        ~gslX680_ts_init~, ...). ~dtbo.img~ had no matches. A parallel search
        across every extracted partition (vendor, system, odm, product,
        vendor_dlkm, odm_dlkm, all ~_a~ slots - ~_b~ slots are all empty on
        this single-slot device) found no ~.ko~/~.ko.gz~/~.ko.xz~ module and
        no firmware/config file matching silead/gsl by name or content.
      - *What this means*: the vendor driver is compiled *directly into the
        monolithic kernel* (not a loadable module) - which is exactly why
        it was never found in any partition filesystem; it was never there
        to find. This is the well-known out-of-tree "gslX680" vendor driver
        family (widely forked on GitHub by other Chinese tablet vendors off
        the original Silead SDK) - a different driver from mainline's
        ~silead.c~, and one that bakes the panel's calibration table into a
        C header at build time rather than loading it from a separate
        firmware file at runtime the way mainline does.
      - The real DT compatible string this vendor used:
        ~"GSL,GSL3673"~/~"GSL,GSL3673_800X1280"~ (comma-separated, uppercase
        - not the lowercase ~silead,gsl3673~ mainline convention). ~800x1280~
        almost certainly names this panel's specific calibration variant
        among several the vendor driver supports.
      - Every other content-grep hit in this pass (inside ~pcbtest.apk~,
        font/cert files, ~libbluetooth.so~, ~.oat~/~.apex~ files, several
        Google apps' ~.apk~s) is very likely coincidental byte matches
        inside compressed/compiled binaries, not real touchscreen files - a
        short pattern like ~gsl3~ turns up this kind of noise when grepped
        against binary content; none of these are plausible touchscreen
        locations and none are worth chasing.
      - *Revised next step*: since there's no separate firmware blob to
        extract from a partition, the path forward is either (a) find a
        public ~gslX680~/~GSL3673~ driver fork on GitHub whose embedded
        calibration table matches this panel (~800x1280~, i2c1 0x40 - the
        same identifying details already confirmed on real hardware), and
        feed that table through
        [[https://github.com/onitake/gsl-firmware][onitake/gsl-firmware]]'s
        ~untscfg~ to produce the blob mainline's ~silead.c~ expects via
        ~request_firmware()~; or (b) extract the calibration table directly
        out of ~boot.img~'s kernel binary (harder - needs locating the raw
        byte table near these strings, not just reading strings). (a) is
        much easier if a matching public fork exists - worth a targeted
        GitHub search (e.g. ~gsl3673 800x1280~) before attempting (b).
      - *Found and built (2026-09-28), option (a)*: GitHub turned up
        [[https://github.com/54shady/qop_kernel/blob/master/drivers/input/touchscreen/gsl3673_800x1280.c][54shady/qop_kernel's ~gsl3673_800x1280.c~/~.h~]]
        (commit ~f016d717b21b38ae115f92a276a58913f1040035~, GPLv2,
        "Copyright (c) 2012 Shanghai Basewin") - an exact identifying match,
        not just "a" GSL3673 driver: its I2C address (~0x40~), its DT

        integrator that supplied this exact reference file to many
        unrelated Chinese tablet OEMs sharing this chip+panel combination -

        circumstantial evidence gets, and loading firmware into the touch
        controller's RAM at runtime is fully non-destructive/reversible
        either way - nothing here risks the hardware.

        ~gsl-firmware~'s own tools fit this source format (~fw_extractor~

* DONE Audio (RK817 codec) — headphones, built-in speaker, jack detect
  - *Update 2026-10-01 (patch 0021)*: the speaker works. Stock's
    ~spk-ctl-gpios~ (GPIO3_A2) is the external amplifier's enable; the
    accelerometer never used that pin as an IRQ (stock ~irq_enable = 0~),
    so our patch 0013 had it wrong and caused an IRQ storm at every boot
    ("irq 61: nobody cared"). The amp is fed from the headphone stage
    (Playback Mux ~HP~), as Rockchip's driver does with
    ~use-ext-amplifier~. Headphone detect on GPIO3_A1 (active low).
    Tests ~test_11~ (by hand), ~test_12~ (patched kernel). The notes
    below are the history; where they say otherwise, this wins.
  - Volume buttons and automatic speaker mute on plug-in: user space,
    ~debian/p25t-audio-keys.sh~ (triggerhappy), confirmed 2026-10-01
    (~tests/test_14.sh~ shows the events). See debian.org.
  - Still open: the microphone. Android records (low level), so it
    exists; here capture is silent. Next step when picked up: compare
    the stock codec's mic settings (~rockchip,mic-in-differential~,
    capture volume) with mainline's controls.
  - Patch 0015 (2026-09-27): wired ~vccio_acodec~ (LDO_REG4, 3.3 V) as
    ~pmu_io_domains~' ~vccio1-supply~, the codec's ~mclk~ (~&cru
    I2S1_MCLKOUT_TX~, no BSP-only ~codec {}~ subnode - mainline's
    driver wants these on ~pmic@20~ itself), a ~rk817-sound~
    simple-audio-card node, and enabled ~&i2s1_8ch~ (~status =
    "disabled"~ by default, same shape as GPU before patch 0014). RK817
    register-level change, explicitly proposed and approved before
    being made. Config fix (whole ~CONFIG_SOUND~ subsystem was off)
    checked and applied proactively before the build. See
    [[file:kernel.org][kernel]] for the full writeup, including two
    unrelated deployment snags (a missing ~LOCALVERSION=~ that broke
    Wi-Fi/Bluetooth, and the boot partition running out of space from
    accumulated old backups) and how they were fixed.
  - Deliberately *not* wired: ~spk-ctl-gpios~ (stock's speaker-amp
    enable pin is the same physical GPIO already confirmed as the
    accelerometer's IRQ - can't be both) and
    ~rockchip,mic-in-differential~ (mic wiring unknown).
  - *Confirmed on hardware 2026-09-27*: ALSA card ~RK817~ registered,
    playback + capture PCM present. ~speaker-test~ over the headphone
    jack (mux at its default ~HP~) - clean, audible tone. This meets
    the original ask ("audio would be a nice feature").

    - Built-in speaker stays silent even with the codec's ~Playback
      Mux~ switched to ~SPK~ (~amixer -c0 cset numid=4 SPK~) - the mux
      only picks the codec's internal output stage, it doesn't
      substitute for whatever hardware GPIO enables the external
      amplifier. The real amp-enable pin for *this* board is unknown
      (stock's value is taken by the accelerometer IRQ) and would need
      identifying some other way (schematic, or trial of unused GPIOs)
      before it can be wired.
    - Mic capture: ~arecord~ + ~aplay~ round-trip produced no audible
      sound. Mic wiring on this board was already unconfirmed going in
      (see hardware.org); no capture-source-select control shows up in
      ~amixer~ either, so there's no way to tell from software alone
      whether a mic is physically present. Not investigated further
      without more information.

* DONE Power button doesn't wake it from off unless USB cable is plugged in
  - *Closed 2026-10-01, not reproducible*: under Android, without any
    cable, the power button starts the tablet normally. The earlier
    observation fits the drained battery found on 2026-09-26.
  - Found 2026-09-25, reported 2026-09-26 (unrelated to the USB host-mode
    DTB, patch 0007): with the tablet fully off and no cable, pressing the
    power button does nothing. Plugging a USB-C cable into the PC makes it
    power on by itself, no button press needed.
  - Very likely NOT a software issue on our side. The decision to power on
    from a fully-off state is made by the RK817 PMIC's own hardware state
    machine (ONKEY debounce, VBUS-presence auto-boot), *before* the SoC
    boot ROM runs — i.e. before U-Boot, our kernel, our DTB or the
    initramfs get to execute at all. We have never written to the RK817 on
    the real hardware (only read-only dumps, plus the "rails" LDO
    experiment which was only ever exercised in an emulated PMIC, never on
    the tablet) - see [[file:findings.org][findings]].
  - Auto-boot-on-VBUS is a common, intentional PMIC/charger feature on
    Android devices and is probably factory behavior, not something we
    configured.
  - Best isolation test (cheap, no risk): remove the SD card so the
    tablet boots stock Android, and try the power button with no cable.
    If it also fails to turn on, this is stock hardware/firmware
    behavior, nothing to do with this project.
  - Possible causes if it turns out to be real: aged/near-empty battery
    (the 4.28 V reading was taken while charging, not at rest), a
    battery-protection cutoff that needs VBUS to release, or the power
    button itself needing a longer hold than usual.
  - Supporting data point (2026-09-26): after months of disuse the tablet
    was found at a literal 0%, unusually low for it - consistent with a
    battery-protection cutoff and/or a long-idle self-discharge, either of
    which would need VBUS to release/recover before the ONKEY press can
    do anything. Strengthens the "stock hardware behavior on this
    particular, long-idle battery" reading over a software cause.
  - Practical workaround for testing (e.g. the USB host-mode DTB, which
    needs no PC cable once running): power on with the PC cable plugged
    in as usual, wait for it to boot, then unplug the PC and plug in the
    USB receiver instead - the DWC3 host controller enumerates whatever
    is connected at the time, so it doesn't need to be the receiver at
    the moment of power-on.
  - Do not attempt a fix by writing RK817 registers without proposing it
    first - this touches power-on/charging logic, not just a display or
    Wi-Fi rail.

* DONE Multiple VT sessions — on-demand getty spawning
  - *Solved 2026-09-30*: ~serial-getty@ttyGS0~ blocked for ever
    resetting ~ttyGS0~ (nobody reading it) while holding systemd's
    ~/dev/console~ lock; every getty started after it waited on that
    lock. Evidence ~tests/result_10a~ to ~result_10h~, write-up in
    [[file:findings.org][findings]]. Fix: the unit is masked, tty2/tty3
    are no longer enabled statically, logind's on-demand tty2-tty6 work,
    logout respawn works, reboots finish. History below kept for
    reference; where it contradicts this, this wins.
  - Motivation: the user wants at least two usable sessions on the panel
    at once - one normal-user, one for ~sudo -i~/root - without juggling a
    single shell. ~tty1~ (normal user) already existed; ~tty2~/~tty3~
    were meant to be logind's on-demand ~autovt@.service~, spawned the
    moment you first switch to that VT (Ctrl+left-Alt+F2/F3).

  - *Symptom*: Ctrl+Alt+F2/F3 switched the panel to a fresh-looking VT
    (later, ~chvt 2~ confirmed the switch itself works), but no working
    login shell ever appeared. Keystrokes visibly echoed on screen but
    never reached the login prompt - a password typed at the "login:"
    prompt stayed visible (no echo suppression), and Enter did nothing.

  - *Ruled out first* (both confirmed fine, not the cause):
    - The VT-switch mechanism itself: ~chvt 2~ works cleanly once run
      from a real root shell (~sudo su -~, then ~chvt 2~) - plain ~sudo
      chvt 2~ fails with "Couldn't get a file descriptor referring to
      the console", because ~sudo~'s ~use_pty~ default routes the
      command through a pty, which breaks ~chvt~'s console-ioctl-based
      fd detection. A generic sudo/kbd-package gotcha, unrelated to our
      kernel/DT.
    - The keymap: ~dumpkeys~ confirmed plain Alt/Ctrl+Alt+F2 already map
      to ~Console_2~ (only AltGr+F2 maps elsewhere) - matches the left
      Alt key the user was actually using. Not a keymap bug.

  - *Root of the real problem*: the getty processes never acquire a
    controlling terminal (ctty). ~ps aux~ showed ~?~ in the TTY column
    for every VT getty (~tty1~-~tty3~'s PIDs), while the serial/gadget
    getties (~ttyGS0~, ~ttyS2~) correctly showed their own tty. ~fuser
    -v /dev/tty2~ confirmed the getty process does hold the device open
    - but ~strace -p <pid> -e trace=read,write -f~ while typing on that
    live VT screen showed *zero* syscalls: the keystrokes are visibly
    echoed by the kernel's own VT layer but never reach the getty
    process at all, because it was never given that terminal as its
    ctty in the first place.

  - *Related, not fully disentangled*: mid-investigation,
    ~systemctl stop getty@tty2.service~ (and a couple of other
    ~systemctl~ commands) failed outright with "Failed to get load
    state of getty@tty2.service: Connection timed out" - systemd/PID1's
    own control socket was unresponsive, not just the one getty. Most
    likely caused by the repeated manual enable/disable/kill/strace-attach
    cycles during testing, but not proven separate from the underlying
    bug. A direct bypass, ~sudo agetty tty2 linux~ (run manually,
    outside systemd), did redraw a real "p25t login:" prompt - but login
    still hung after the username with no shell, same ctty-acquisition
    symptom, and a second manual attempt immediately printed "Hangup"
    and exited. Recovered via ~sudo reboot -f~ (plain ~sudo reboot~ hung
    on the same unresponsive control socket; ~-f~ bypasses it with a
    direct kernel ~reboot(2)~ syscall).

  - *Confirmed after a clean reboot*: ~getty@tty2.service~, switched
    from on-demand ~autovt@tty2~ to a *static* enable (started as part
    of the normal boot sequence, the same way ~tty1~ always was), came
    up working - clean login, real ctty. ~tty3~, still left on
    ~autovt@tty3~'s on-demand path at that point, showed the exact same
    broken symptom as before. This matched the user's own hunch ("Maybe
    the create ttys on request doesn't work at all") - so ~getty@tty3~
    was enabled statically too, the same way.

  - *Newest finding, this refines the diagnosis further*: even a
    statically-enabled getty that came up clean at boot fails the exact
    same way once you *log out* of it - logging back in without a
    reboot doesn't work, same broken-ctty symptom recurs. So the real
    boundary isn't "static enable vs. on-demand autovt" - it's "the
    unit's very first, boot-time start" vs. *any later (re)start*,
    whatever triggers it: logind's on-demand autovt spawn, a manual
    ~systemctl restart~/~enable --now~, or the getty's own automatic
    respawn after the previous session on that VT exits. None of those
    later starts reliably acquire a controlling terminal on this
    system; only the boot-time one does.

  - *Root cause*: NOT understood yet. Not chased further live, per
    explicit instruction, without more hands-on time on the actual
    hardware. Candidates worth checking first if this gets picked back
    up: something in the VT/console kernel config or DT
    (~CONFIG_VT~/~CONFIG_FRAMEBUFFER_CONSOLE~/~CONFIG_DRM_FBDEV_EMULATION~,
    or how ~fbcon~ hands the VT over - possibly linked to the "blinking
    cursor after a cable-less boot" item above), or a systemd/logind
    behavior specific to this VT/fbcon setup rather than anything in
    our own patches.

  - *Current practical status (workaround, not a fix)*: ~getty@tty2~
    and ~getty@tty3~ are now enabled statically in ~p25t-setup.sh~,
    alongside ~tty1~ - piggybacking on the one start that's known to
    work (boot) gives the user the normal-user-plus-root sessions they
    wanted, on ~tty1~-~tty3~. See "Multiple sessions on the panel" in
    [[file:debian.org][debian]]. *Known limitation*: treat those three
    sessions as long-lived, not something to casually log out of -
    once you exit a session on any of them, getting back in currently
    needs a full reboot, not just switching VTs again.

  - *Leads (2026-09-30, research + code review, nothing tested yet)*.
    Evidence script: ~tests/test_10.sh~ (read-only; ~vt 4~ mode switches
    VT and back). Run it on a blinking-cursor boot, a good boot, with
    ~vt 4~, and after a logout; note USB-C role and cable each time.
    - H1, strongest: *PID 1 itself blocks* on a tty. Every symptom fits:
      no getty (re)start after boot, ~systemctl~ "Connection timed out",
      ~login~ hanging (pam_systemd → logind → PID 1), ~reboot~ needing
      ~-f~. Known elsewhere with a serial getty on a port nobody
      listens to, including USB gadget ~ttyGS0~ - our
      ~serial-getty@ttyGS0~ in normal mode without a cable, on a gadget
      that is already flaky. The ~TTYReset~/~TTYVHangup~ clean-up PID 1
      does when that getty exits is the suspected blocking point. Fits
      "normal mode: no login".
    - H2: the getty's ~(agetty)~ child waits for ever in systemd's
      ~acquire_terminal()~ because another session still owns the VT.
    - H3: logind skips ~autovt@ttyN~ because the VT looks busy at that
      instant (systemd #23660, #39462) - explains tty4-6 only.
    - H4 (blinking cursor only): the prompt is there but not drawn;
      ~/dev/vcs1~ shows the VT text regardless of the panel.
    - Why Debian normally has tty1-6: only ~getty@tty1~ is enabled;
      tty2-6 come from logind's ~NAutoVTs=6~, started on the first
      switch to that VT - so H1/H3 would explain their absence here.
    - Cheap cross-check later (a change, needs OK): one boot with
      ~serial-getty@ttyGS0~ masked, or in host mode (no ttyGS0 at all).
